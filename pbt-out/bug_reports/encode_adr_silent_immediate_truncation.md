# Bug Report — `encode_adr` silently truncates out-of-range immediates

**File:** `src/backend/arm/assembler/encoder/load_store.rs`
**Function:** `encode_adr`
**Severity:** High (silent mis-compilation — wrong PC-relative address, no diagnostic)
**Found by:** property-based test `prop_encode_adr_tests::prop_out_of_range_immediate_rejected`

## Summary

`encode_adr` accepts an arbitrary `i64` immediate and packs it into the ADR
21-bit signed immediate field using bit-masking (`& 3` for `immlo`,
`& 0x7FFFF` for `immhi`) **without validating the encodable range**. The code
itself flags this with a `TODO: validate 21-bit signed immediate range`.

Immediates outside the legal range `[-2^20, 2^20-1] = [-1048576, 1048575]` are
**silently truncated** instead of being rejected, producing an ADR instruction
that loads a *different* address than the source requested — with no error.

## Relevant code

```rust
pub(crate) fn encode_adr(operands: &[Operand]) -> Result<EncodeResult, String> {
    let (rd, _) = get_reg(operands, 0)?;
    // TODO: validate 21-bit signed immediate range
    if let Some(Operand::Imm(imm)) = operands.get(1) {
        let imm = *imm;
        // ADR: 0 immlo[1:0] 10000 immhi[18:0] Rd
        let immlo = ((imm as u32) & 3) << 29;
        let immhi = (((imm as u32) >> 2) & 0x7FFFF) << 5;
        let word = immlo | (0b10000 << 24) | immhi | rd;
        return Ok(EncodeResult::Word(word));
    }
    ...
}
```

## Spec basis

ARMv8-A Architecture Reference Manual, §C4.1.64 *ADR*: the immediate is a
21-bit signed PC-relative offset, encodable range `-1048576` to `+1048575`.
The architecture mandates the assembler reject out-of-range offsets.

GNU `as` confirms the contract — it errors on overflow:

```
$ echo 'adr x0, #1048576' | aarch64-linux-gnu-as -
<stdin>:1: Error: immediate out of range
```

## Reproduction (minimal failing input)

Property input: `adr x0, #1048577`  (i.e. `2^20 + 1`)

```
encode_adr(vec![Operand::Reg("x0"), Operand::Imm(1048577)])
  => Ok(Word(0x30800000))     // expected: Err(...)
```

Decoding `0x30800000` back through the ADR field map:

| field | bits | value |
|-------|------|-------|
| op    | [31] | 0     |
| immlo | [30:29] | `01` |
| immhi | [23:5]  | `0x40000` |
| Rd    | [4:0] | 0 |

`sign_extend(immhi:immlo)` = `sign_extend(0x100001, 21)` = **`-1048575`**.

So `adr x0, #1048577` is silently compiled as **`adr x0, #-1048575`** — the
address loaded is off by `2097152` bytes (2 MiB) from what the programmer
wrote, in the *opposite direction*. The bug is symmetric for negative
overflow (e.g. `adr x0, #-1048577` wraps to `+1048575`).

## Impact

- **Silent mis-compilation.** Any ADR with `#imm` outside `[-1 MiB, +1 MiB]`
  (e.g. generated by a codegen pass computing a large PC-relative offset, or
  hand-written assembly) emits a word targeting the wrong address.
- **No diagnostic.** Unlike `encode_prfm` (which validates `imm12` range and
  returns `Err`) or `encode_ldr_str` (which falls back to an alternate form),
  `encode_adr` returns `Ok`.
- The relocation (`AdrPrelLo21`) form is unaffected — only the literal
  `#imm` path is broken.

## Suggested fix

After resolving `Operand::Imm(imm)`, range-check before packing:

```rust
if !(-(1i64 << 20)..(1i64 << 20)).contains(&imm) {
    return Err(format!(
        "adr: immediate {} out of range [-1048576, 1048575]", imm
    ));
}
```

(Or, for consistency with the rest of the crate, accept the wider `i64` but
emit the relocation form — though the literal-`#imm` form is by definition a
resolved value and should be range-checked.)

## Test artifact

The failing property is checked in at
`src/backend/arm/assembler/encoder/load_store.rs`,
module `prop_encode_adr_tests::prop_out_of_range_immediate_rejected`. It
asserts the spec'd `is_err()` contract; it will pass once the fix above is
applied. The five passing properties (`golden_anchored_encodings`,
`prop_imm_round_trips`, `prop_op_bits_and_sign_bit`,
`prop_symbol_form_relocation`, `prop_reg_second_operand_rejected`)
independently confirm that in-range immediates, field placement, op bits, and
the `AdrPrelLo21` relocation path are all correct.
